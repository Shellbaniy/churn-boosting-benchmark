## Проект

Статья и репозиторий «Сравнительный анализ алгоритмов градиентного бустинга XGBoost, LightGBM и CatBoost на задаче прогнозирования оттока клиентов».

- Датасет: Telco Customer Churn (7043 строки, целевая переменная `Churn`). CSV лежит в `data/raw/` (обычно называется `WA_Fn-UseC_-Telco-Customer-Churn.csv`).
- Цель: работа уровня middle+ ML-инженера. Важны воспроизводимость, корректная методология и аккуратные выводы, а не рекордная метрика.
- Главная идея статьи: на таком размере данных разница между моделями, скорее всего, окажется в пределах шума. Вывод строится на статистической проверке, а не на формулировке «победил на 0.003».

## Обязательные компоненты

1. **EDA.**
   - Дисбаланс классов: график и доля оттока (около 26.5%), объяснение, почему accuracy не подходит.
   - Пропуски `TotalCharges`: колонка читается как `object`, по известным данным 11 пустых строк, все при `tenure == 0`. Проверить на реальном файле, показать таблицей, обосновать заполнение нулём вместо медианы.
   - Типы признаков, дубликаты, удаление `customerID`.
   - 3–4 содержательных графика связи с оттоком (`Contract`, `tenure`, `InternetService`, `PaymentMethod`), а не десятки однотипных.

2. **Два пайплайна.**
   - A (унифицированный): одинаковый препроцессинг для всех моделей (OHE + числовые признаки). Сравнивает именно алгоритмы.
   - B (нативный): CatBoost с `cat_features`, LightGBM с `category` dtype, XGBoost с `enable_categorical=True`. Сравнивает модели «как задумано авторами».

3. **Baseline.** `DummyClassifier`, `LogisticRegression` (scaling + OHE), три модели с дефолтными параметрами в обоих пайплайнах.

4. **Optuna.**
   - Одинаковый бюджет trials для всех моделей, одни и те же CV-фолды, фиксированные seeds.
   - TPE sampler, `MedianPruner`, early stopping внутри trial.
   - Пространства поиска описать таблицей (диапазоны, log-scale для learning rate и регуляризации).
   - Сохранить optimization history и param importances.
   - Тюнинг только на train через CV.

5. **Финальный бенчмарк на отложенном тесте.**
   - Split 80/20, стратифицированный, фиксированный seed. Тест не трогать до этого этапа.
   - Метрики: ROC-AUC, PR-AUC, F1, recall, Brier score или calibration curve, время обучения и инференса.
   - Порог подбирать на валидации (по F1 или по бизнес-стоимости), не на тесте.
   - Бизнес-метрика: ожидаемая прибыль по порогам или lift / recall@top-10%, с явно помеченными допущениями о стоимости удержания и потери клиента.

6. **Статистическая значимость.**
   - Repeated stratified k-fold (5x5 или 10x3) для зафиксированных лучших конфигураций.
   - Попарное сравнение через corrected resampled t-test (Nadeau & Bengio).
   - Bootstrap-доверительные интервалы для ROC-AUC на тесте и bootstrap разницы между парами моделей.
   - McNemar для сравнения на пороге, поправка Holm на множественные сравнения, размер эффекта.
   - Тест Фридмана не использовать: датасет один.
   - Честно описать ограничение: гиперпараметры подбирались на тех же данных, оценка слегка оптимистична. Nested CV с урезанным бюджетом trials как возможное улучшение.

7. **SHAP и визуализации.**
   - `TreeExplainer` на тестовой выборке: beeswarm, bar, 2–3 dependence plot (`tenure`, `MonthlyCharges`, `Contract`), один waterfall для конкретного клиента.
   - Сравнение важностей признаков между моделями через ранговую корреляцию Спирмена.
   - Оговорка про коррелированные признаки (`TotalCharges`, `tenure`, `MonthlyCharges`).

8. **Статья** в академичной структуре: аннотация, введение и постановка задачи, данные и EDA, методология (алгоритмы, пайплайны, схема валидации, метрики), эксперименты, статистический анализ, интерпретация, обсуждение и ограничения, заключение и рекомендации, литература.

9. **Репозиторий.** `src/`, `configs/`, `tests/`, `notebooks/` (только EDA и итоговые графики), `reports/figures/`, `Makefile`, `requirements.txt` с версиями, README с таблицей результатов, графиками, инструкцией воспроизведения и ограничениями. Логирование запусков в MLflow.

## Жёсткие требования

- Никакой утечки данных: весь препроцессинг только внутри `sklearn` `Pipeline` / `ColumnTransformer` и внутри CV-фолдов.
- Воспроизводимость: фиксированные seeds, версии в `requirements.txt`, одна команда на этап через `Makefile`.
- Не выдумывать результаты: все числа в статье и README берутся только из реальных запусков.
- ROC-AUC на Telco обычно около 0.84–0.85. Заметно выше означает, что нужно искать утечку.
- Ограничения исследования указывать честно в статье и README.

## Стиль кода

- Чистый код без декоративных разделителей и баннеров в комментариях. Комментарии короткие и только там, где они действительно нужны.
- Осмысленные `print`: что именно считается и какой получился результат (размеры выборок, доля оттока, число пропусков, метрики, p-value и вывод теста). Вывод должен явно показывать выполнение требований из списка выше.
- Код живёт в модулях `src/`, а не в ноутбуках. Функции с type hints.
- Минимум 3 теста на `pytest`: нет утечки, форма данных, детерминизм.
